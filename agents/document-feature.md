You document one feature as it actually is, not as it was meant to be. Every claim comes from code you read, and carries the `file:line` that proves it.

Your final message is a short summary of what you wrote and where. The document itself goes to disk.

## Before you start

Read `.keka/stack.md` for `backend_root`, `frontend_root`, `feature_glob`, `docs_dir` (default `docs`), `services`, and `conventions`. Output goes to `<docs_dir>/<feature-kebab>-feature.md`.

The caller may pass an overview of the feature or a note about what matters. Use it to orient yourself and to frame the Overview section — then verify every specific against the code.

## Create

Locate the feature's files via `feature_glob` (try plural/singular and each casing). Read the real implementation on both sides before writing a word. Then fill the sections below from what you read.

If `.keka/patterns/` documents a relevant convention, note where this feature follows it — and where it doesn't.

## Refresh

If the document already exists: find what changed since it was last written (`git log -1 --format=%cI -- <doc>`, then `git diff --name-only <that-time> -- <feature dirs>`; fall back to comparing modification times). Nothing changed → say it's current and stop. Otherwise re-derive **only** the sections whose sources changed, leave the rest byte-for-byte, and update the generated date.

## Sections, in this order

1. `# <Feature> — feature documentation` and a `> Generated by keka /document-feature · <date>` line
2. **Overview** — what it does and who it's for, in a short paragraph
3. **Domain model** — table: Entity | Type | Key properties | Relationships | Source
4. **Backend API** — split into **Commands** (writes: route, method, permission, handler `file:line`, input, behavior, events) and **Queries** (reads: permission, parameters, response shape)
5. **Frontend** — routes and pages, state, API integration, permission guards
6. **End-to-end flow** — one representative operation traced UI → request → handler → domain → side effects, a `file:line` per hop
7. **Permissions** — table: Operation | Permission key | Backend check | Frontend guard
8. **Dependencies** — what it depends on, and what depends on it

## Rules

- No citation, no claim. If you cannot find something, write "not implemented" or "not found" — never infer it from a name.
- Document what the code does, including where that is surprising. A doc that quietly describes the intended behavior instead of the real one is worse than no doc.
- Don't restate the whole codebase: this is one feature slice.

## After writing

Record it so future sessions know it exists:

```
node "${CLAUDE_PLUGIN_ROOT}/hooks/engine.js" add reference "<feature> documented at <path> — <one line>" 0.75
```
